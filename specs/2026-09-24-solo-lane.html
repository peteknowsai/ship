Ship's solo lane

Recommended changes to the ship plugin so every app runs the same way: work in a worktree, test on real links, say "merge main", and it goes live, with the database, hosting and sign-in in step. 2026-09-24.

In one line: Three phases: build, test, land. Ship pushes each worktree's branch early and keeps a draft PR as the roadmap record. When the build is done, ship proves it works on the branch's own links, then hands them to you and waits. You try it. You say "merge main". Ship merges the PR, and the app's own build ships the database first and then the app. Each repo only declares its facts: how to print its links, how to run it locally, how test sign-in works, how to check its wiring, and what going live deploys.

The flow, for every app

1 · BuildWorktree, pushed at once with a draft PR; pushed again at each milestone, links posted each time
→
2 · TestShip first: gates, review, a verify walk on the preview link, the stack check. Then you try the links. Ship waits here
→
3 · LandOn your "merge main": rebase, gates, stack check, merge the PR. Live in minutes; worktree removed; live links in the result

Orange is where you come in. Ship's own review sits inside Test, before you are cued, so you only ever try something that already passed. The stop at Test applies to every lane wherever main is live; "looks good" is not "merge main".

The three services, in step

Local and previews

  • Convex: the app's dev deployment
  • Clerk: test keys, any address signs in
  • Vercel: a private branch link per app
  • Safe to break anything

Production

  • Convex: the app's prod deployment, pushed by the build with its deploy key, drop check first
  • Clerk: live keys on the app's own domain
  • Vercel: the custom domain is public, every vercel.app URL stays behind your login

Never

  • A preview on prod data
  • Production on test sign-in
  • A prod push by hand
  • An env file edited to aim somewhere

Decisions for you

Does EXPRESS wait for "merge main" too?

Recommended: yes, wherever main is live. A one-line fix still reaches real people, and your word is the only thing standing between a push and production. A repo whose main deploys nothing can declare land: auto and keep landing on green.

Verify on the preview, or on localhost?

Recommended: the preview when a repo has one, since that is the real host, database and sign-in you will test. It costs the five minutes of a build. Localhost stays the fallback and the quick look.

PRs or not?

Settled: a draft PR per branch, as the record on GitHub. It never waits for a reviewer and never merges on its own.
